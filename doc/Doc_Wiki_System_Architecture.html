1. 概述

Doc-Wiki 是一个 Claude Code Skill，将真实源码转成可验证的、离线可用的技术文档。支持三种文档类型（module/system/guide），共享一套设计系统（6 套皮肤、暗色模式、响应式布局），通过 17 类自动化校验保证质量。

详细说明

1.1 背景

AI 生成的技术文档存在普遍问题：编造代码引用、视觉风格不一致、缺乏可验证性。 Doc-Wiki 通过7 条铁律（先读后写、不许编造、颜色锁死、零装饰、零外链、每图必说、引用溯源） 和17 类自动化校验解决了这些问题。

核心理念：把真实源码转成可验证的、离线可用的工程文档。不是营销页、不是 PPT——是"读完能上手干活"的技术文档。

2. 分层架构

Doc-Wiki 采用五层架构：SKILL.md（路由+规则）→ references/（工作流）→ templates/（骨架）→ scripts/（工具链）→ examples/（样本）。每层职责清晰，通过文件引用和占位符约定解耦。

架构详解

五层架构

Doc-Wiki 采用五层架构，每层职责单一，通过文件引用和占位符约定解耦。 这种分层设计的核心优势是独立演进——新增文档类型只需添加 reference + template， 不影响校验逻辑；新增校验规则只需修改 validate-doc.js，不影响模板结构。

层间依赖是单向的：L1（路由）→ L2（工作流）→ L3（模板）← L4（工具链）← L5（样本）。 L4 和 L3 之间通过 @sync 标记实现双向同步，但这是开发时的同步，不是运行时的依赖。

层级目录职责关键文件 L1: 路由层SKILL.md文档类型路由、执行模式选择、铁律定义、工作流编排SKILL.md L2: 工作流层references/每种文档类型的详细 Phase 0→1→2→3 流程*-workflow.md, html-components.md L3: 模板层templates/HTML 骨架（CSS/JS 内嵌）、MD 模板、章节模板*.html, sections/*.html L4: 工具链层scripts/校验、转换、同步、皮肤切换、设计系统validate-doc.js, md-to-html.js L5: 样本层examples/各文档类型的黄金样本，对照参考*-content-example.html
设计决策 五层架构而非单一配置文件，是因为文档生成涉及路由决策（选类型）、内容规范（怎么写）、 视觉规范（怎么排版）、质量校验（怎么检查）四个独立关注点。 分层使得每层可以独立演进——新增文档类型只需添加 reference + template，不影响校验逻辑。

3. Skill 核心（SKILL.md）

SKILL.md 是整个系统的入口，包含文档类型路由、执行模式选择、7+1 条铁律、内容驱动深度规则、普通模式工作流（Phase 0→1→2→3）和全力模式工作流（7 阶段）。

核心机制详解

3.1 文档类型路由

用户触发后，SKILL.md 根据意图关键词自动路由到四种文档类型。路由规则基于触发词匹配—— 用户说"模块文档"或"给 X 写文档"时路由到 module，说"系统设计"时路由到 system， 说"项目指南"或"guide"时路由到 guide。意图不明确时，必须用 AskQuestion 让用户选择。

确定类型后，立即读取对应 reference 文件获取详细工作流指导，同时读取 html-components.md 获取共享组件规范。

触发词路由目标详细流程
"模块文档"、"给 X 写文档"modulereferences/module-workflow.md
"系统设计"、"架构设计"systemreferences/system-workflow.md
"项目指南"、"guide"guidereferences/guide-workflow.md
"分模块写文档"、"批量生成"batch循环复用 module 流程

3.2 执行模式

确定文档类型后，SKILL.md 必须询问用户选择执行模式。普通模式适合日常文档需求，单 agent 单次完成； 全力模式适合高质量文档需求，采用多 subagent 并行分析 + 深度研究 + 多轮自审，不计 token 消耗。

全力模式的核心差异在于：不区分文档类型，自动分析项目并生成完整文档体系（系统架构 + 核心模块 + Guide + 索引页）。

模式特征适用场景
⚡ 普通模式单 agent 单次完成，快速生成日常文档需求
🔥 全力模式多 subagent 并行 + 深度研究 + 多轮自审高质量文档需求

3.3 内容驱动深度

模板只定义"可用的组件库和章节池"，不硬编码输出的章节数量和深度。 章节取舍的判据是源码复杂度，不是模板框架。这是 Doc-Wiki 最重要的设计决策之一—— 传统的文档模板会预定义固定的章节结构（如"必须有 12 章"），导致简单模块被迫填充无意义的章节， 复杂模块又被强制压缩到有限的章节中。

Doc-Wiki 的解决方案是：源码驱动深度。一个 30 行的工具函数不需要 12 章； 一个 2000 行的状态机模块可能每章都要。每章的最低内容密度也有明确要求—— 每个 ## H2 章节必须包含 ≥2 段叙述性文字 + ≥1 个结构化元素。

文档类型源码规模最低章节数最低代码块
module< 200 行5 章3
module200-1000 行7 章5
module> 1000 行9+ 章8
system3-5 模块6 章-
system> 10 模块10+ 章-
设计决策 内容驱动深度而非模板驱动，是因为一个 30 行的工具函数不需要 12 章， 而一个 2000 行的状态机模块可能每章都要。章节取舍的判据是源码复杂度，不是模板框架。

4. 模板引擎

模板引擎采用骨架+内容分离模式：HTML 模板提供骨架（CSS/JS 内嵌），agent 生成内容填入 {{SECTIONS}} 占位符。支持渐进式披露三层结构（Summary → Details → Deep Dive）。

模板机制详解

4.1 骨架+内容分离

模板引擎的核心设计是骨架+内容分离——HTML 模板提供完整的骨架（CSS/JS/sidebar/TOC）， agent 只负责生成内容片段填入 {{SECTIONS}} 占位符。这确保了所有文档的视觉一致性， 无论由哪个 agent 生成。

骨架包含：DOCTYPE、charset、viewport、内嵌的 CSS（通过 @sync 标记）、侧边栏 TOC、 主内容区域、暗色模式切换按钮、内嵌的 JS（通过 @sync 标记）。agent 生成的内容只需是合法的 HTML 片段， 不需要包含任何样式或脚本。

HTML 模板（templates/*.html）
  ├── CSS（@sync:doc-shell.css:start/end 内嵌）
  ├── JS（@sync:doc-shell.js/start/end 内嵌）
  ├── HTML 骨架（head, body, sidebar, main）
  └── {{SECTIONS}} 占位符 ← agent 生成的内容填入这里

4.2 @sync 同步机制

三个共享运行时文件（CSS/JS/Skin）通过 @sync 标记嵌入模板。 当 CSS 或 JS 修改后，运行 inline-shared.js --sync 自动替换所有模板中的对应区域。

// inline-shared.js 同步逻辑
const SHARED_FILES = {
  'doc-shell.css': path.join(SCRIPTS_DIR, 'doc-shell.css'),
  'doc-shell.js': path.join(SCRIPTS_DIR, 'doc-shell.js'),
  'skin-switcher.js': path.join(SCRIPTS_DIR, 'skin-switcher.js'),
};

// 替换模板中 @sync:xxx:start ... @sync:xxx:end 区域
function syncTemplate(templatePath, sharedContent) {
  let html = fs.readFileSync(templatePath, 'utf8');
  for (const [name, content] of Object.entries(sharedContent)) {
    const startMark = `/* @sync:${name}:start */`;
    const endMark = `/* @sync:${name}:end */`;
    const re = new RegExp(`${startMark}[\\s\\S]*?${endMark}`, 'g');
    html = html.replace(re, `${startMark}\n${content}\n${endMark}`);
  }
  fs.writeFileSync(templatePath, html, 'utf8');
}

模板专属的 CSS 覆盖（如 module 的 --max-width: 880px）位于标记区域之外，不受同步影响。

文件职责大小同步命令

doc-shell.jsTOC/ScrollSpy/高亮/缩放/Mermaid~15KB

4.3 渐进式披露章节模板

7 个章节模板，每个遵循三层渐进式披露结构。这种结构的设计灵感来自 DeepWiki 和 ZRead.ai—— 读者可以快速扫描 Summary 判断是否需要深入，大多数读者只需阅读 Details 层， 高级读者可以展开 Deep Dive 获取实现细节和边界情况分析。

模板使用 {{占位符}} 标记需要填充的内容，agent 替换占位符后即可生成完整的章节 HTML。 每个模板都包含设计决策 Callout 和 Sources 块，确保内容有 WHY 解释和源码溯源。

5. 校验流水线

validate-doc.js 实现 17 类自动化校验，覆盖内容质量、视觉约束、交互功能三个维度。--fix 可自动修复部分问题，--test-interactive 启用全力模式交互测试。

校验项详解

17 类校验项

校验脚本采用插件式架构，每类检查是一个独立函数，通过 Report 对象收集结果。 --fix 模式下，Mermaid 块、heading ID、代码块等可自动修复；其他问题报告后由 agent 就地修复。

// validate-doc.js 校验架构
function validateFile(filePath, fix) {
  let html = fs.readFileSync(filePath, 'utf-8');
  const report = new Report(path.basename(filePath));

  // 17 类校验
  html = checkMermaid(html, report, fix);        // 1. Mermaid 语法
  html = checkHeadingIds(html, report, fix);      // 2. 标题 ID
  html = checkCodeBlocks(html, report, fix);      // 3. 代码块
  checkTables(html, report);                       // 4. 表格结构
  checkInlineMarkdown(html, report);               // 5. 内联 MD
  checkCollapsibleSections(html, report);          // 6. 折叠章节
  html = checkTOC(html, report, fix);             // 7. TOC 完整性
  checkHtmlSkeleton(html, report);                 // 8. HTML 骨架
  checkSourceRefs(html, report);                   // 9. 源码引用
  checkGlossary(html, report);                     // 10. 术语表
  checkScopeBlock(html, report);                   // 11. Scope 声明
  checkVisualConstraints(html, report);            // 12. 视觉约束
  checkSvgGuardrails(html, report);                // 13. SVG 护栏
  checkFigCaptions(html, report, isNewDoc);        // 14. 图说完整性
  checkEmptySections(html, report);                // 15. 空章节
  checkDuplicateContent(html, report);             // 16. 重复内容
  checkContentDensity(html, report);               // 17. 内容密度

  // 交互测试（全力模式）
  if (testInteractive) {
    checkProgressiveDisclosure(html, report);      // I1. 渐进式披露
    checkInteractionFeatures(html, report);        // I2-I7. 交互功能
  }
}

Report 对象收集所有检查结果后，按类别分组输出，统计 pass/warn/fail/fix 数量。

交互测试（--test-interactive）

交互测试是全力模式的专属功能，验证文档的交互特性是否正常工作。 这 7 项测试覆盖了渐进式披露、折叠/展开、代码高亮、暗色模式、响应式布局、搜索友好和图表交互—— 这些是 DeepWiki/ZRead 级别文档的必备交互能力。

交互测试与内容校验是互补的——内容校验确保"写得对"，交互测试确保"用得好"。 全力模式下，两类测试都必须通过才能交付。

6. 运行时系统

运行时由三个共享文件组成：CSS 设计系统（6 套皮肤 + 暗色模式）、JS 交互功能（TOC/ScrollSpy/代码高亮/图表缩放）、皮肤切换器。所有文档类型共享同一套运行时。

运行时详解

6.1 设计系统（doc-shell.css）

CSS 设计系统定义了完整的视觉规范，所有文档类型共享同一套 CSS 变量。 设计系统的核心理念是约束即自由——通过严格的变量约束（禁止硬编码颜色、禁止渐变、禁止大阴影）， 确保所有生成的文档具有一致的视觉风格，无论由哪个 agent 生成。

CSS 变量分为语义层（--text, --bg, --accent）和组件层（--callout-info, --code-bg）， 语义层在暗色模式下自动切换，组件层通过 var(--xxx, fallback) 确保离线可用。

6.2 交互功能（doc-shell.js）

doc-shell.js 实现了 6 项核心交互功能，所有功能采用 try-catch 包裹的 features[] 数组模式， 单个功能失败不影响其他功能。主题切换采用 3 层回退：localStorage 保存 → OS 偏好检测 → 默认 light。

TOC 自动生成扫描所有 h2/h3 标签，生成侧边栏导航；ScrollSpy 使用 IntersectionObserver 高亮当前章节；图表缩放支持点击全屏 + 滚轮缩放 + Esc 关闭；Mermaid 暗色模式在主题切换时自动重渲染。

6.3 皮肤系统（skin-switcher.js）

皮肤系统提供 6 套预设视觉风格，通过覆盖 CSS 变量实现。每套皮肤定义了完整的颜色方案 （背景、文字、强调色、代码高亮等），切换时只需更新 data-skin 属性。 皮肤选择保存在 localStorage 中，下次打开时自动恢复。

皮肤设计遵循约束即自由原则——所有皮肤共享相同的字号梯度、间距规则和圆角限制， 只在颜色方案上做差异化。这确保了无论选择哪个皮肤，文档的排版和结构始终保持一致。

皮肤色调适用场景 Teal青绿色（默认）通用技术文档 Editorial编辑风格长文阅读 Vellum羊皮纸色经典风格 Mono单色灰度打印友好 Carto高对比度演示展示 Signal信号风格嵌入式/硬件文档

7. 全力模式

全力模式是 Doc-Wiki 的高级工作流，不区分文档类型，自动分析项目并生成完整文档体系。采用 7 阶段流程：项目探测→任务规划→并行分析→深度研究→内容生成→自审→修订循环→交付。

全力模式详解

7.1 七阶段流程

全力模式的核心创新是不区分文档类型——普通模式需要用户先选类型再生成， 全力模式自动探测项目结构，一次性生成完整文档体系。这消除了用户的选择负担， 也避免了"选错类型导致文档不完整"的问题。

另一个关键设计是独立审核 subagent（铁律 §8）——生成者自审容易"自我感觉良好"， 独立审核者用"新鲜眼光"审查，更容易发现问题。审核采用 6 维度评分（总分 60，≥ 50 通过）， 不通过时返回修订清单，主 agent 按清单逐项修改后重新审核，最多循环 5 轮。

阶段执行者动作输出 0. 项目探测主 agent扫描目录、统计规模、识别技术栈项目概况报告 1. 任务规划主 agent规划 subagent 任务表任务分配计划 2. 并行分析多 subagent同时读取源码，返回结构化发现知识图谱 3. 深度研究主 agent + 补充gap-driven 补充 + 外部参考补充分析 + 参考摘要 4. 内容生成主 agent生成完整文档体系HTML 文档集 5. 自审独立审核 subagent6 维度评分（总分 60）审核报告 + 修订清单 6. 修订循环主 agent按修订清单逐项修改（最多 5 轮）修订后文档 7. 交付主 agent校验 + 交互测试 + 质量报告最终文档 + 质量报告

7.2 产出物

全力模式一次性生成完整文档体系，不需要用户选择类型。系统架构文档覆盖整个项目的分层架构和模块职责； 核心模块文档为每个核心模块生成独立的 API 参考和实现细节；端到端 Guide 沿数据流叙事，适合新人上手； 索引页提供所有文档的导航入口。

产出物之间有清晰的引用关系——系统架构文档引用各模块文档，Guide 引用系统架构和模块文档， 索引页汇总所有文档。这形成了一个自洽的文档体系，而非孤立的文档集合。

7.3 自审评分体系

自审采用 6 维度评分体系，每个维度 0-10 分，总分 60 分。通过线设为 50/60（83%）， 这是"高质量但不追求完美"的平衡点——设得太高会导致过多轮循环，设得太低则质量提升不明显。

审核 subagent 必须返回结构化结果：总分、各维度分数、修订清单。修订清单包含具体的操作（补充/修正/增加）、 目标位置（章节编号）和详细说明。主 agent 按清单逐项修改，每项完成后标记 done。

维度满分评分标准 准确性10代码引用真实、API 签名正确 完整性10覆盖所有核心模块、不遗漏关键流程 深度10解释 WHY、算法分析、性能说明 可操作性10读者能照着上手、代码示例可运行 结构10章节层次清晰、编号一致、术语表完整 视觉合规10符合全部铁律、CSS 变量、无硬编码色

通过线：≥ 50/60（83%）

8. 数据流

Doc-Wiki 的数据流沿两个方向流动：正向（源码→文档）和反向（校验→修复）。正向流经 SKILL.md 路由→reference 指导→template 骨架→agent 内容填充→校验交付。

数据流详解

8.1 正向流：源码→文档

正向流是文档生成的主流程，从用户触发到最终交付。每个阶段的输出是下一阶段的输入， 形成清晰的管道。SKILL.md 负责路由决策，references 负责内容规范，templates 负责视觉骨架， agent 负责内容填充，validate-doc 负责质量把关。

关键设计：agent 生成的内容是HTML 片段（填入 {{SECTIONS}}），而非完整 HTML 文件。 骨架（CSS/JS/sidebar/TOC）由模板提供，确保视觉一致性。

用户触发（"写文档"）
  → SKILL.md 路由（判断类型 + 选择模式）
  → references/*-workflow.md（指导 Phase 0→1→2→3）
  → Phase 0: 读源码（记录 file:line）
  → Phase 1: 结构设计（选章节框架）
  → Phase 2: 内容生成（填入模板 {{SECTIONS}}）
  → Phase 3: 校验交付（validate-doc.js 17 类检查）

8.2 反向流：校验→修复

反向流是质量保障的核心机制。校验脚本发现问题后，分为两类处理： --fix 可自动修复的问题（如 Mermaid 语法、heading ID）直接写回文件； 不可自动修复的问题（如视觉违规、空章节）报告给 agent 就地修复。

修复后重新校验，形成"生成→校验→修复→再校验"的闭环。新文档必须所有校验通过才能交付。

validate-doc.js 发现问题
  → report.fail() / report.warn()
  → --fix 自动修复（Mermaid、heading ID、代码块）
  → agent 就地修复（视觉违规、空章节）
  → 重新校验直到通过

8.3 同步流：CSS/JS→模板

同步流确保三个共享运行时文件的修改能自动传播到所有 HTML 模板。 这解决了"改了 CSS 忘了同步模板"的一致性问题——只需运行一条命令，所有模板自动更新。

每个模板通过 @sync 标记区域嵌入共享内容，模板专属的 CSS 覆盖位于标记区域之外， 不受同步影响。这使得每个文档类型可以有独特的视觉调整（如 module 的 --max-width: 880px）， 同时共享完整的设计系统。

修改 doc-shell.css / doc-shell.js / skin-switcher.js
  → node inline-shared.js --sync
  → 替换 templates/*.html 中 @sync 标记区域
  → 所有模板自动更新
