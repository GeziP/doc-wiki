Scope: 本文覆盖 SmartFactory 嵌入式工控系统的端到端数据流、核心模块交互、配置系统和故障排查。 不覆盖 MES 侧工单生成逻辑和硬件电气设计。

1. 概述

SmartFactory 是一个嵌入式工控系统，控制产线上的机械臂、传送带和质检设备。 系统接收来自 MES（制造执行系统）的工单，将其分解为设备指令序列，调度执行并采集运行数据。

本文档面向新接手项目的开发者，帮助你理解数据如何从 MES 工单流经系统， 最终变成设备动作和质检报告。阅读完成后，你应该能独立修改配方参数并排查常见故障。

设计决策 系统不直接与 MES 通信。RecipeManager 从本地文件系统读取工单 JSON，MES 通过 FTP 将文件推送到约定目录。这样做是因为工控网络与 IT 网络物理隔离，无法直接 HTTP 调用。

2. 快速开始

Config

前置条件

  • GCC 11.4+ 或 ARM 交叉编译工具链
  • CMake 3.24+
  • FreeRTOS 10.5 SDK（已包含在 vendor/）

克隆并构建

cmake -B build && cmake --build build

准备配方文件

cp config/sample-recipe.json config/recipe.json

启动仿真模式

./build/smartfactory --sim

启动后控制台输出如下，表示系统就绪：

[INFO] RecipeManager: loaded recipe "sample-recipe" v1.2
[INFO] SequenceEngine: compiled 12 tasks from recipe
[INFO] TaskScheduler: ready, 4 priority levels active
[INFO] DeviceDriver: SIM mode — no Modbus connection
[INFO] System ready. Awaiting commands...
注意 仿真模式下 DeviceDriver 不连接真实设备。所有 Modbus 指令会被记录到 logs/sim-commands.log 而不是发送到 PLC。生产环境启动时去掉 --sim 参数。

3. 配置

Config

系统配置位于 config/system.yaml:1-80， 下面是关键字段及其具体含义：

scheduler:
  max_queue_size: 256          # 调度队列上限，超过则拒绝新任务
  time_slice_ms:               # 各优先级层的时间片（毫秒）
    critical: 0                # 0 = 无限制，立即执行到完成
    high: 100
    normal: 50
    low: 20
  starvation_guard_ms: 500     # 防饥饿：每层至少每 500ms 被调度一次

device:
  protocol: modbus_tcp
  host: "192.168.1.100"        # PLC 地址
  port: 502
  timeout_ms: 2000             # 通信超时，超过视为设备离线
  retry_count: 3               # 超时后重试次数

starvation_guard_ms 是防止低优先级任务饿死的关键参数。如果你的产线有大量实时控制任务， 可以适当增大到 1000ms，但不建议超过 2000ms，否则清理任务积压会导致内存增长。

4. 核心流程

Runtime

一个完整的生产周期从 MES 推送工单开始，到质检报告生成结束。 数据在系统中经过 5 个阶段：

1. 接收JSON 工单 → RecipeManager
→
2. 编译Recipe → Task[]
→
3. 调度MLFQ 优先级排序
→
4. 执行Modbus → PLC
→
5. 采集结果 → SQLite

4.1 配方编译（Recipe → Task）

SequenceEngine 的 compile() 方法 （sequence_engine.cpp:45-80） 将配方中的每个步骤转换为一个 Task 对象。例如，下面的配方步骤：

{
  "step": "move_arm",
  "params": { "axis": "X", "position": 150.0, "speed": 80 },
  "priority": "high",
  "depends_on": ["home_position"]
}

会被编译为一个 Task，优先级设为 HIGH（数值 1）， 并在 DependencyGraph 中建立对 home_position 任务的依赖边。 只有当 home_position 完成后，这个 move_arm 任务才会进入 Ready 状态。

设计决策 编译阶段会进行拓扑排序检测循环依赖。如果配方中存在 A→B→C→A 的环，编译直接失败并返回 CycleDetectedError，而不是等到运行时死锁。这比运行时检测的成本低 10 倍以上。

7. 完整示例：单工单生产周期

Example

场景设定

MES 推送一个 3 步工单：机械臂归零 → 移动到取料位 → 抓取工件。我们跟踪这个工单的完整生命周期。

输入：配方文件

{
  "recipe_id": "R-2026-0516",
  "version": "1.0",
  "steps": [
    { "id": "home",     "action": "home_all",  "priority": "critical" },
    { "id": "move",     "action": "move_arm",  "priority": "high",
      "params": { "axis": "X", "position": 150.0 },
      "depends_on": ["home"] },
    { "id": "grip",     "action": "grip",      "priority": "high",
      "params": { "force": 30 },
      "depends_on": ["move"] }
  ]
}

运行时流程

home_allCRITICAL → 立即执行
→
move_arm依赖 home ✓ → Ready
→
grip依赖 move ✓ → Ready

输出结果

时间任务状态耗时
T+0mshome_allRunning → Completed320ms
T+320msmove_armRunning → Completed450ms
T+770msgripRunning → Completed180ms

SELECT task_id, state, duration_ms FROM task_log
WHERE recipe_id = 'R-2026-0516';

-- task_id  | state     | duration_ms
-- home     | completed | 320
-- move     | completed | 450
-- grip     | completed | 180

8. FAQ / 排障

启动报 "Modbus connection refused"

检查 config/system.yaml 中 device.host 和 device.port 是否正确。 确认 PLC 已上电且在同一子网。用 ping 192.168.1.100 验证网络连通性。

如果只是开发调试，加 --sim 参数启动仿真模式。

任务一直卡在 Pending 状态

通常是依赖的上游任务失败或被取消。运行 smartfactory --status 查看所有任务状态， 找到状态为 Failed 的上游任务。级联取消机制会自动取消下游，但 Pending 任务不会被取消—— 它们只是永远等不到依赖满足。

修复方法：smartfactory --cancel-stale 清理所有无法满足依赖的 Pending 任务。

内存持续增长

检查 starvation_guard_ms 配置。如果设得太大（>2000ms），低优先级的清理任务 得不到及时执行，导致完成的任务对象堆积在内存中。建议保持默认值 500ms。
