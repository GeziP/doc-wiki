# 文档维护工作流程

更新以证据为依据，保留正确内容，避免全量重写。共享契约见 SKILL.md；改写规则见 [writing-quality.md](writing-quality.md)。

## M0：确定快照与漂移范围

- 有源码对齐 commit 元数据时，从该 commit 比较目标源码 diff。
- 没有元数据时用文档/源码提交记录作为线索，再核对实现；提交日期和 commit message 不能证明行为漂移。
- 用户点名范围则先核对该范围，发现相关影响时说明关联关系。
- 记录目标文档、源码快照、已知线索和未知项。关联源码不限于 src/，按项目实际目录。

## M1：核对

对照文档与受影响实现/调用点/测试，输出：文档位置、当前源码事实(file:line)、建议修改、严重度、证据等级。
API/行为失真优先，随后引用过时和补充缺失。已知线索只是引导，不能代替核对。
普通模式可自行核对；用户要求全力/并行工作时使用 fullpower 的分工与审核。

## M2：最小修订

1. 按证据修订，保留未漂移内容，保持主体、条件、数字、例外和不确定性。
2. 刷新修改章节及关联复述的行号；跨接口同名字段分别核对。
3. 沿用项目版本与元数据约定，记录源码快照和修改范围，不强制每次加大版本。
4. 用同一版本工具重新生成修订文档，不顺手 --all 重刷无关产物。
5. 如目标项目 vendored 工具，先明确本轮使用哪个副本；仅本次授权范围内需要修工具时同步相关副本并验证。

## M3：问题基线

修订前后使用相同工具版本、目标集合和检查配置；分别保存 HTML 与语言 JSON。实际命令见 [quality-tooling.md](quality-tooling.md)。
问题身份包含文件、规则、严重度及内容键；位置移动不必代表新问题。同身份的新增副本仍算新增。
默认阻断新增 error；strict 同时阻断新增 warning。可以减少历史问题，不能用减少旧问题抵消新问题。
不把“错误集合完全一致”作为目标，正确判据是“没有新增阻断问题”。
新增目标或改变配置需要有意重新建立基线；不能用不兼容的基线掩盖结果。
基线通过只表示无新增机械问题，不能抵消语义错误。

## M4：聚焦审核与交付

核对修改章节及关联引用/复述，审核 API、行为、条件、术语、示例；全力模式独立审核见 [fullpower-workflow.md](fullpower-workflow.md)。
审核修订后重跑 M3；严重事实错误、错误 API、关键条件遗漏不能交付为通过。
交付范围、快照、新增/解决问题、实际检查与未确认项。

历史记录反映当时实现与经验，下面的日期/计数不作为通用规则或当前项目事实。
